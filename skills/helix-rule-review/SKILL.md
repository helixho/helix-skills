# helix-rule-review

把规则当作一组“情境 → 动作”的条件句，检查它们能否对每个情境给出唯一、可执行的结论。只判断逻辑：不评价文风、篇幅和文件位置，不核实规则所依据的事实。

## 范围

- 只审查用户指定的对象：文件、段落或草案。判断条款关系需要其他规则时，只读与结论相关的部分。
- 草案用标题和原句定位，不编造行号。

## 方法

1. **形式化**：把每条规则改写为“情境 → 动作”，写出隐含的例外和适用范围。说不清情境或动作的条款，本身就是问题。
2. **检查**：按下面七项检查条款自身及条款之间的关系。
3. **反例**：每个问题都给出一个具体情境，说明规则在该情境下互相矛盾、无规可依或可得出多种动作。举不出反例的不报。

## 七项检查

1. **矛盾**：同一情境同时被要求做和不做，或被要求做两个不能并存的动作。区分用户已确认的政策替换与未决冲突：前者按确认处理；后者列出双方原句，说明取舍，由用户决定新的权限边界。
2. **空档**：并列条件没有覆盖全部情境，某些情境无规可依；缺少默认分支也算。
3. **优先级**：多条规则同时适用且结论不同，文本没有说明谁优先，结果取决于阅读顺序。修正时按特殊优先于一般、后定优先于先定、用户当前要求优先于文件写明关系。
4. **概念一致**：同一概念用了不同的词，同一个词指不同的概念，或关键词边界不清，导致不同读者得出不同动作。
5. **适用与执行**：读者能判断何时适用、做什么、何时算完成。适用条件过宽（在不该适用的情境也触发）或过窄都算问题；只写禁止的条款要补上应做的动作。“必要”“合理”等需要判断的词，只在会导致不同动作时才算问题。
6. **冗余与无效**：条款能从其他条款推出（冗余），或模型默认就会这样做、删掉不改变行为（无效）。冗余只保留一处；两处会导出不同动作时按矛盾处理。
7. **引用有效**：条款引用的章节、文件或条目确实存在，被引用处的含义与引用方的理解一致。

## 输出

- 先给结论：通过，或按影响排序的问题。
- 每个问题写明类型、原句与位置、反例情境和最小修正，并标明是文字修正，还是会改变授权或工作方式。
- 修正后对改动处用同样七项复查，确认没有引入新问题。
- 没有问题就报告通过，不为凑数量制造问题。
- 逻辑审查不能证明模型实际遵守规则；未做行为实测时明确说明。
