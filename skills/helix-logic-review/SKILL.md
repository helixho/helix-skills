# helix-logic-review

检查一组规则或一段论证在逻辑上是否成立：规则能否对每个情境给出唯一、可执行的动作；论证的结论能否由前提推出。只判断逻辑：不评价文风、篇幅和文件位置，不核实规则或论证所依据的事实本身。

## 范围

- 只审查用户指定的对象：文件、段落、草案或一段论证。判断关系需要其他材料时，只读与结论相关的部分。
- 草案用标题和原句定位，不编造行号。
- 只报告问题和修正建议，不修改被审查对象；用户要求修改时，按要求修改后对改动处复查。

## 方法

1. **形式化**：规则改写为“情境 → 动作”，论证改写为“前提 → 结论”，并写出隐含的例外、适用范围和前提。说不清情境、动作或前提的条款，本身就是问题。
2. **检查**：规则按七项检查；论证按七项中的第 1、4、7 项和第 5 项的全称措辞检查，再加四项论证检查。规则和论证混在一起时按条款分别归类。条款自身和条款之间的关系都要检查。
3. **反例**：每个问题都给出一个具体情境，说明规则在该情境下互相矛盾、无规可依或可得出多种动作，或论证在该情境下前提成立而结论不成立。找方案的反例时，可先假设方案已经失败，倒推最可能导致失败且现在就能验证的条件。举不出反例的不报；冗余与无效类问题没有这种反例，改以“可由哪条推出”或“删除后行为不变”为证据。

## 七项检查

1. **矛盾**：同一情境同时被要求做和不做，或被要求做两个不能并存的动作；论证中前后结论或数据冲突。区分用户已确认的政策替换与未决冲突：前者按确认处理；后者列出双方原句，说明取舍，由用户决定新的权限边界。
2. **空档**：并列条件没有覆盖全部情境，某些情境无规可依；缺少默认分支也算。
3. **优先级**：多条规则同时适用且结论不同，文本没有说明谁优先，结果取决于阅读顺序。修正时按特殊优先于一般、后定优先于先定、用户当前要求优先于文件写明关系。
4. **概念一致**：同一概念用了不同的词，同一个词指不同的概念，或关键词边界不清，导致不同读者得出不同动作或结论。“其”“该”“上述”等指代必须落到唯一对象。
5. **适用与执行**：读者能判断何时适用、做什么、何时算完成。适用条件过宽（在不该适用的情境也触发）或过窄都算问题；“所有”“任何”“必须”“一律”等全称措辞，检查是否有未写明的例外。工作流中每一步依赖的输入要在之前的步骤已经产出，步骤之间不能循环依赖。只写禁止的条款要补上应做的动作。“必要”“合理”等需要判断的词，只在会导致不同动作时才算问题。
6. **冗余与无效**：条款能从其他条款推出（冗余），或模型默认就会这样做、删掉不改变行为（无效）。冗余只保留一处；两处会导出不同动作时按矛盾处理。
7. **引用有效**：引用的章节、文件、条目或承诺的后续内容确实存在，被引用处的含义与引用方的理解一致。

## 论证另查四项

1. **依据支撑结论**：结论的范围和强度不超过依据，包括由个例推出普遍结论、把“可能”说成“必然”，以及前提里已经预设了结论（循环论证）。
2. **因果成立**：没有把相关或先后关系当作因果，没有因果倒置，也没有漏掉同样能解释结果的其他原因。
3. **前提写明**：结论依赖的隐含前提和适用条件已写出，关键前提按现有材料标明属于有依据、待验证还是存在反证；前提不成立时结论随之失效的，要指明。
4. **手段达成目标**：方案类论证把目标和手段分开，检查手段能否实现目标，是否满足目标、预算、时间和权限等约束；约束不能同时满足时明确指出。

## 输出

- 先给结论：通过，或按影响排序的问题。审查多个对象时，先按对象分组列出问题，再按影响汇总排序。
- 每个问题写明类型、原句与位置、反例情境和修正，并标明是文字修正，还是会改变授权、工作方式或结论。
- 修正写成可直接替换原句的改写。修正需要补充依据才能成立时，写明需要补充什么，不编造依据。
- 论证推不出结论时，写“依据不足以支持”，不判定结论为假。
- 修正后对改动处用同样的检查复查，确认没有引入新问题；自己提出的修正和替代方案适用同一标准。
- 没有问题就报告通过，不为凑数量制造问题。
- 逻辑审查不能证明模型实际遵守规则，也不能证明前提为真；未做行为实测或事实核实时明确说明。
